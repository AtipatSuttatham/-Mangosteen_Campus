# API ล็อกอิน (`/api/auth/`)

> สัญญาระหว่าง backend กับ frontend — ฝั่งเว็บอ้างอิงไฟล์นี้ ไม่ต้องเดา
> โค้ดอยู่ที่ `backend/accounts/` (views.py, tokens.py, services.py, registration.py) test ที่ `backend/accounts/test_auth_api.py` และ `test_registration_api.py`

## แนวคิด (อ่านสั้น ๆ)
- **access token** อายุ 15 นาที — เว็บเก็บ **ในหน่วยความจำเท่านั้น** (ไม่ใช้ localStorage) แล้วส่งใน header `Authorization: Bearer <access>`
- **refresh token** อายุ 7 วัน — เก็บใน **httpOnly cookie** ที่โค้ดหน้าเว็บอ่านไม่ได้ เบราว์เซอร์ส่งให้เองเฉพาะเส้นทาง `/api/auth/`
- เมื่อ access หมดอายุ (หรือเปิดหน้าใหม่ที่ยังไม่มี access) เว็บเรียก `refresh` เพื่อขอ access ใหม่ — เรียกครั้งไหน ระบบจะหมุนเวียน: ใบแลกเดิมใช้ไม่ได้อีก และได้ cookie ใบใหม่
- **role ใน token ใช้แสดงเมนูเท่านั้น** สิทธิ์จริงของแต่ละวิชา backend ตรวจจากฐานข้อมูลทุกครั้ง

## กฎที่ frontend ต้องทำตาม
1. ทุกคำขอไป backend ใช้ path ขึ้นต้นด้วย `/api` (Vite proxy ตอน dev)
2. เรียก `refresh` และ `logout` ต้องส่ง header **`X-Requested-With: fetch`** (ค่าอะไรก็ได้ที่ไม่ว่าง) และแนบ cookie (`credentials: "same-origin"`) — ไม่มี header นี้จะได้ 403 (กัน CSRF)
3. แสดงข้อความ error โดยใช้ **`code`** เป็นกุญแจแปลไทย/อังกฤษ ไม่แสดง `detail` จาก backend ตรง ๆ
4. อย่าเก็บ access token ลง localStorage/sessionStorage/cookie ที่โค้ดอ่านได้
5. เรียก `refresh` **ครั้งละคำขอ** ต่อแท็บ (ถ้ามีหลายส่วนต้องการ token พร้อมกันให้รอผลคำขอเดียวกัน) เพราะใบแลกใบเดิมใช้ได้ครั้งเดียว

## Endpoint

### `POST /api/auth/login/`
เข้าสู่ระบบ — ช่องเดียวรับทั้งอีเมลและรหัสนักศึกษา/พนักงาน (**มี `@` = อีเมล, ไม่มี = รหัส**)

คำขอ (JSON)
```json
{ "identifier": "somchai@example.com", "password": "..." }
```
- อีเมล: ไม่สนตัวพิมพ์เล็ก/ใหญ่ ตัดช่องว่างหัวท้าย
- รหัส: **แยกตัวพิมพ์เล็ก/ใหญ่** (`T0042` ≠ `t0042`) ตัดช่องว่างหัวท้าย

สำเร็จ `200` + ตั้ง cookie `refresh_token`
```json
{
  "access": "<access token>",
  "user": { "id": 1, "email": "...", "student_or_staff_id": "T0042", "role": "teacher",
            "first_name": "...", "last_name": "...", "first_name_en": "", "last_name_en": "",
            "is_email_verified": true, "avatar_url": "" }
}
```
ล้มเหลว

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 401 | `invalid_credentials` | ไม่พบผู้ใช้ / รหัสผ่านผิด / บัญชีถูกปิด / ยังไม่ได้ตั้งรหัสผ่าน (ข้อความเดียวกันทุกกรณี) |
| 403 | `email_not_verified` | รหัสผ่านถูก แต่ยังไม่ยืนยันอีเมล (บอกเฉพาะเมื่อรหัสผ่านถูก) |
| 400 | `validation_error` | ไม่ส่ง `identifier` หรือ `password` |

### `POST /api/auth/register/`
สมัครเองด้วยอีเมล — ได้บัญชี **ผู้เรียน (`student`) เสมอ** ที่ยังไม่ยืนยันอีเมล และ **ยังไม่ล็อกอินให้** (ไม่มี cookie/token กลับมา) ระบบส่งลิงก์ยืนยัน (อายุ 24 ชั่วโมง) ไปที่อีเมล

คำขอ (JSON) — ช่องอื่นที่ส่งมา (เช่น `role`) ถูกทิ้งทั้งหมด
```json
{ "email": "manee@example.com", "password": "...", "first_name": "มานี", "last_name": "ใจดี" }
```
- อีเมล: ตัวพิมพ์เล็ก/ใหญ่ไม่มีผล ตัดช่องว่างหัวท้าย; ชื่อ/นามสกุล: ตัดช่องว่างหัวท้าย ห้ามว่าง ยาวไม่เกิน 150
- รหัสผ่าน: ตรวจตามกฎของระบบ (ยาว ≥ 8 / ไม่ใช่รหัสที่คนใช้กันทั่วไป / ไม่ใช่ตัวเลขล้วน / ไม่คล้ายชื่อหรืออีเมลที่กรอก) — ช่อง "ยืนยันรหัสผ่าน" ตรวจที่หน้าเว็บ ไม่ต้องส่งมา

สำเร็จ `202` + `{}` (หน้าเว็บพาไปหน้า "ตรวจสอบอีเมลของคุณ")

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 400 | `validation_error` | ข้อมูลไม่ครบ/ผิดรูปแบบ/รหัสผ่านไม่ผ่านกฎ — ดู `errors` (ข้อความ) และ **`error_codes`** (รหัสของแต่ละกฎ ใช้แปลข้อความ) ของแต่ละช่อง |
| 409 | `email_taken` | อีเมลนี้มีบัญชียืนยันแล้ว หรือบัญชีถูกปิด → ให้ผู้ใช้เข้าสู่ระบบ/ลืมรหัสผ่านแทน |

`error_codes` ของรหัสผ่านที่เป็นไปได้: `password_too_short`, `password_too_common`, `password_entirely_numeric`, `password_too_similar` (ช่องอื่น: `required`, `blank`, `invalid`, `max_length`)

พฤติกรรมที่ควรรู้
- **สมัครซ้ำด้วยอีเมลที่ยังไม่ยืนยัน:** ตอบ `202` เหมือนสมัครใหม่ ระบบเขียนทับรหัสผ่านและชื่อด้วยค่าล่าสุด แล้วส่งลิงก์ใหม่ (ฉบับเก่าใช้ไม่ได้) — ป้องกันคนร้ายสมัครล่วงหน้าด้วยอีเมลของผู้อื่นแล้วรอเจ้าของกดลิงก์ ถ้าซ้ำภายใน 60 วินาที จะอัปเดตข้อมูลแต่ไม่ส่งอีเมลซ้ำ
- **ส่งอีเมลไม่สำเร็จ** (ระบบอีเมลล่ม): ยังตอบ `202` (บันทึก error ฝั่งเซิร์ฟเวอร์) ผู้ใช้กด "ส่งอีกครั้ง" ได้

### `POST /api/auth/verify-email/`
ยืนยันอีเมลด้วยโทเคนจากลิงก์ `{FRONTEND_URL}/verify-email?token=...` — **ใช้ POST ไม่ใช่ GET** เพราะโปรแกรมสแกนลิงก์ของอีเมลเปิดลิงก์ล่วงหน้า ถ้าเป็น GET ลิงก์จะถูกใช้ไปก่อนที่ผู้ใช้กด: หน้าเว็บ `/verify-email` อ่าน `token` จาก URL แล้วเรียก endpoint นี้เอง

คำขอ (JSON): `{ "token": "..." }`

สำเร็จ `200` `{ "email_verified": true }` — **ไม่ล็อกอินให้** พาผู้ใช้ไปหน้า login (ตามหน้า "ยืนยันอีเมลแล้ว" ใน wireframe)

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 400 | `token_invalid` | ไม่มีโทเคนนี้ / ใช้ไปแล้ว / ถูกแทนที่ด้วยลิงก์ฉบับใหม่ / เป็นลิงก์ผิดจุดประสงค์ / บัญชีถูกปิด |
| 400 | `token_expired` | โทเคนถูกต้องแต่หมดอายุ → เสนอให้ขอลิงก์ใหม่ |
| 400 | `validation_error` | ไม่ส่ง `token` หรือว่าง/ยาวเกิน |

### `POST /api/auth/resend-verification/`
ขอลิงก์ยืนยันอีเมลใหม่ (ลิงก์ฉบับก่อนหน้าใช้ไม่ได้ทันที)

คำขอ (JSON): `{ "email": "manee@example.com" }`

ตอบ **`202` + `{}` เหมือนกันทุกกรณี** — ไม่มีอีเมลนี้ / ยืนยันแล้ว / บัญชีถูกปิด / ยังไม่พ้น 60 วินาทีจากลิงก์ล่าสุด / ส่งแล้ว — เพื่อไม่ให้ใครใช้ endpoint นี้เดาว่าอีเมลไหนมีบัญชี ระบบส่งอีเมลจริงเฉพาะบัญชีที่ยังไม่ยืนยัน เปิดใช้งาน และพ้น 60 วินาที หน้าเว็บควรแสดงข้อความ "ถ้ามีบัญชีนี้ เราส่งลิงก์ให้แล้ว" และนับถอยหลังปุ่มเอง

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 400 | `validation_error` | อีเมลว่าง/ผิดรูปแบบ |

### `POST /api/auth/refresh/`
แลกใบแลก (จาก cookie) เป็น access ใหม่ + หมุนเวียนใบแลก — ไม่ต้องมีเนื้อหาคำขอ ต้องมี header `X-Requested-With`

สำเร็จ `200` — รูปแบบเดียวกับ login (ได้ `access` + `user` ล่าสุด และ cookie ใบใหม่) ใช้ตอนเปิดเว็บใหม่เพื่อกู้สถานะล็อกอินได้เลยโดยไม่ต้องเรียก `me` แยก

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 401 | `invalid_refresh_token` | ไม่มี cookie / หมดอายุ / ถูกใช้ไปแล้ว / ออกจากระบบแล้ว / บัญชีถูกปิด (ระบบลบ cookie ให้) → ให้พาไปหน้า login |
| 403 | `missing_requested_with_header` | ลืมส่ง header |

### `POST /api/auth/logout/`
เพิกถอนใบแลกและลบ cookie — ต้องมี header `X-Requested-With` ตอบ `204` เสมอ (เรียกซ้ำหรือไม่มี cookie ก็ไม่ error) เว็บควรล้าง access token ในหน่วยความจำด้วย
> access token ที่ออกไปแล้วยังใช้ได้จนหมดอายุ (สูงสุด 15 นาที) แต่ขอใหม่ไม่ได้อีก

### `GET /api/auth/me/`
ข้อมูลผู้ใช้ที่ล็อกอินอยู่ — ต้องส่ง `Authorization: Bearer <access>`

สำเร็จ `200` — เฉพาะ object `user` ตามรูปแบบข้างบน

| สถานะ | `code` | เมื่อไหร่ |
|---|---|---|
| 401 | `not_authenticated` | ไม่ส่ง token |
| 401 | `token_not_valid` | token หมดอายุ/ผิดรูปแบบ/บัญชีถูกปิด → เรียก `refresh` แล้วลองใหม่หนึ่งครั้ง ถ้ายัง 401 ให้ไปหน้า login |

## รูปแบบ error ทั้งระบบ
```json
{ "code": "invalid_credentials", "detail": "ข้อมูลเข้าสู่ระบบไม่ถูกต้อง" }
{ "code": "validation_error", "errors": { "identifier": ["This field is required."] },
  "error_codes": { "identifier": ["required"] } }
```
`error_codes` มีโครงเดียวกับ `errors` แต่เป็นรหัสของแต่ละกฎ ใช้แปลข้อความรายกฎ (เช่นกฎรหัสผ่านข้อไหนไม่ผ่าน)

## ข้อจำกัดที่รู้อยู่ (ยอมรับได้ในตอนนี้)
- **ออกจากระบบในแท็บหนึ่ง แท็บอื่นยังเห็นว่าล็อกอินอยู่** จนกว่า access token หมดอายุ (สูงสุด 15 นาที) แล้วจะถูกส่งไปหน้า login เอง — ปรับให้แท็บอื่นรู้ทันทีได้ภายหลัง (เช่น BroadcastChannel)
- **กดออกจากระบบตอนเครือข่ายล่ม:** หน้าเว็บล้างสถานะทันที แต่ cookie ฝั่งเซิร์ฟเวอร์อาจยังใช้ได้จนหมดอายุ (7 วัน) เปิดเว็บใหม่จะกลับเข้าได้
- **สองคำขอ refresh ที่ใช้ cookie ใบเดียวกันพร้อมกันจากคนละที่** อาจสำเร็จทั้งคู่ (ก่อนที่ใบเดิมจะถูกเพิกถอน) — เว็บของเราเรียกทีละคำขอเสมอ จึงไม่เกิดในการใช้งานปกติ

- **`register` บอกว่าอีเมลไหนมีบัญชีแล้ว** (`409 email_taken`) — ผู้ใช้ตัดสินใจเลือกแบบนี้เพื่อความสะดวกของผู้สมัคร แลกกับที่คนนอกไล่เช็กอีเมลได้ (เช่นอีเมลอาจารย์) ต้องมีการจำกัดจำนวนครั้งก่อน deploy เพื่อลดการไล่เช็ก (`docs/pre-deploy-checklist.md`) ส่วน `resend-verification` ไม่บอกอะไรเลย

## สิ่งที่ยังไม่ทำ (ตั้งใจ)
- จำกัดจำนวนครั้งที่ล็อกอินผิด (ผู้ใช้สั่งข้ามไว้ก่อน — **ต้องทำก่อน deploy จริง**)
- บันทึก Audit Log ตอนล็อกอิน/ออกจากระบบ (รอทำระบบ Audit)
- ตั้งรหัสผ่าน / ลืมรหัสผ่าน (ก้อน c3) — สมัคร/ยืนยันอีเมล/ส่งลิงก์ยืนยันใหม่ทำแล้วในก้อน c2
- ลบข้อมูล token ที่หมดอายุแล้วออกจากฐานข้อมูล (มีคำสั่งสำเร็จรูป `flushexpiredtokens` ของ simplejwt ไว้เรียกเป็นครั้งคราว)
