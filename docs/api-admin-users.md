# API จัดการผู้ใช้ของ Admin (`/api/admin/users/`)

> สัญญาระหว่าง backend กับ frontend — หน้าจัดการผู้ใช้ของ Admin อ้างอิงไฟล์นี้ ไม่ต้องเดา
> โค้ดอยู่ที่ `backend/accounts/` (`admin_views.py`, `admin_users.py` (ฝั่งอ่าน), `user_management.py` (ฝั่งเขียน), `admin_serializers.py`, `user_status.py`) และ `backend/common/pagination.py`
> test ที่ `backend/accounts/test_admin_users_api.py`, `test_admin_users_write_api.py`, `test_user_management.py`, `test_user_status.py` และ `backend/common/test_pagination.py`
> มีทั้งฝั่งอ่าน (รายการ + รายละเอียด) และฝั่งเขียน (สร้าง / แก้ / ปิด-เปิดใช้งาน / ส่งลิงก์ตั้งรหัสผ่านซ้ำ) — รายละเอียดการแสดงผลของหน้าเว็บดู `docs/design.md` หัวข้อ "หน้าจัดการผู้ใช้ของ Admin"

## กฎทั่วไป
- ต้องแนบ header `Authorization: Bearer <access>` (วิธีได้ token ดู `docs/api-auth.md`)
- **เฉพาะผู้ใช้ที่มีบทบาท `admin`** — ตรวจจากฐานข้อมูลทุกครั้ง ไม่เชื่อ role ใน token: ไม่ล็อกอิน `401` / ล็อกอินแล้วแต่ไม่ใช่ admin `403` (`code: permission_denied`) / Admin ที่เพิ่งถูกลดบทบาทแล้วถือ token เก่าจะได้ `403` ทันที
- สิทธิ์ตรวจก่อนพารามิเตอร์ ผู้ที่ไม่ใช่ Admin จึงไม่ได้ข้อความ error ของตัวกรอง
- **คำตอบทุกแบบมี `Cache-Control: no-store`** (มีข้อมูลส่วนบุคคล) หน้าเว็บอย่า cache เอง
- คำตอบไม่มีรหัสผ่านหรือค่าแฮชเด็ดขาด (ระบุฟิลด์แบบ whitelist)
- เวลาเป็น ISO 8601 ตามเขตเวลา Asia/Bangkok เช่น `2026-09-20T22:14:00+07:00` (หน้าเว็บนำไปจัดรูปแบบแสดงเอง)
- error ทุกแบบมี `code` ให้ใช้แปลข้อความ (ดู `docs/api-auth.md` หัวข้อรูปแบบ error): เช่น `not_found`, `permission_denied`, `validation_error`

## สถานะบัญชี (`status`)
สถานะไม่ได้เก็บเป็นคอลัมน์ แต่คำนวณจากฟิลด์ที่มี — ผู้ใช้ 1 คนมีสถานะเดียวเสมอ (ยึดลำดับนี้เมื่อเข้าข่ายหลายข้อ):

| ลำดับ | `status` | เงื่อนไข | แสดงเป็น |
|---|---|---|---|
| 1 | `disabled` | `is_active = false` | ปิดใช้งาน |
| 2 | `pending_password` | รหัสผ่านขึ้นต้นด้วย `!` (Admin สร้างให้ เจ้าของยังไม่ตั้งรหัส) | รอตั้งรหัสผ่าน |
| 3 | `pending_verification` | `is_email_verified = false` (สมัครเองแล้วยังไม่กดลิงก์) | รอยืนยันอีเมล |
| 4 | `active` | นอกนั้น | ใช้งานอยู่ |

ค่าเป็นอังกฤษ snake_case หน้าเว็บแปลเป็นไทย/อังกฤษเอง — รายละเอียดการแสดงผล (สี ป้าย) ดู `docs/design.md`

## `GET /api/admin/users/` — รายชื่อผู้ใช้
พารามิเตอร์ (ทุกตัวไม่บังคับ; **ค่าว่าง = ไม่กรอง**):

| พารามิเตอร์ | ค่า | หมายเหตุ |
|---|---|---|
| `role` | `admin` / `teacher` / `student` | ค่าอื่น → `400` (`error_codes.role = ["invalid_choice"]`) |
| `status` | `active` / `pending_password` / `pending_verification` / `disabled` | ค่าอื่น → `400` |
| `search` | ข้อความ ไม่เกิน 100 ตัวอักษร | ดูกฎด้านล่าง; ยาวเกิน → `400` (`error_codes.search = ["max_length"]`) |
| `page` | เลขหน้า เริ่มที่ 1 | **20 รายการต่อหน้า กำหนดขนาดเองไม่ได้** (`page_size` ใน URL ถูกเมิน); หน้าที่ไม่มี/เลขผิด → `404` (`code: not_found`) |

สำเร็จ `200`
```json
{
  "count": 1431, "page": 1, "page_size": 20, "total_pages": 72,
  "next": "http://…/api/admin/users/?page=2", "previous": null,
  "role_counts": { "all": 1431, "admin": 3, "teacher": 142, "student": 1286 },
  "results": [
    { "id": 12, "email": "chaiwat.t@example.com", "student_or_staff_id": "650612044",
      "role": "student", "first_name": "ชัยวัฒน์", "last_name": "ทองดี",
      "first_name_en": "", "last_name_en": "",
      "status": "pending_password", "is_active": true, "is_email_verified": true,
      "last_login": null, "date_joined": "2026-09-20T10:20:00+07:00" }
  ]
}
```
- **เรียง** บัญชีที่สร้างล่าสุดก่อน (`date_joined` ใหม่→เก่า, เท่ากันเรียงด้วย `id` ใหม่→เก่า จึงแบ่งหน้าแล้วไม่ซ้ำ/ไม่ตกหล่น)
- **`role_counts`** = ตัวเลขบนแท็บบทบาท: นับตาม `search` และ `status` ที่ใช้อยู่ แต่ **ไม่นับตาม `role`** (เลือกแท็บผู้สอนแล้วแท็บอื่นยังมีตัวเลข) มีครบ 4 คีย์เสมอ ไม่มีผู้ใช้ = `0`; เมื่อไม่ได้กรอง `role` ค่า `all` เท่ากับ `count`
- **หน้าว่าง:** ไม่พบใครตอบ `200` พร้อม `count: 0`, `results: []`, `total_pages: 1` (ไม่ใช่ 404)
- **`page` ที่เกินหลังเปลี่ยนตัวกรอง:** หน้าเว็บต้องกลับไปหน้า 1 เมื่อเปลี่ยน `role` / `status` / `search`

### กฎการค้นหา (`search`)
- แยกคำด้วยช่องว่าง (ช่องว่างหัวท้ายและซ้ำถูกเมิน) ใช้ **ไม่เกิน 5 คำแรก**
- **ทุกคำต้องเจอ** (AND) และแต่ละคำเจอในฟิลด์ใดฟิลด์หนึ่งก็พอ: ชื่อ, นามสกุล, ชื่ออังกฤษ, นามสกุลอังกฤษ, อีเมล, รหัสนักศึกษา/พนักงาน — เช่น "ณัฐพล เมือง" เจอคนที่มีทั้งสองคำ, "ชัยวัฒน์ 650612044" เจอคนที่ชื่อและรหัสตรงกัน
- **เจอบางส่วนของคำ** (ไม่ต้องขึ้นต้น) และไม่สนตัวพิมพ์เล็ก/ใหญ่
- `%` และ `_` ที่พิมพ์เป็นตัวอักษรธรรมดา ไม่ใช่ตัวแทนของ SQL
- ข้อความว่างหรือมีแต่ช่องว่าง = ไม่ค้นหา

## `GET /api/admin/users/{id}/` — ผู้ใช้ 1 คน (หน้าแก้ไข)
`200` ฟิลด์เดียวกับแถวในรายการทุกตัว **บวก**
```json
{ "updated_at": "2026-09-12T14:05:00+07:00",
  "created_by": { "id": 1, "full_name": "อภิชาติ วงศ์สกุล" } }
```
- `created_by` = ผู้สร้างบัญชี (`null` ถ้าสมัครเอง) ใช้แสดง "สร้างบัญชีโดย ..." ในประวัติบัญชี
- ดู "ประวัติบัญชี" ได้จาก `last_login` (เข้าสู่ระบบล่าสุด, `null` = ยังไม่เคยเข้า), `updated_at` (แก้ไขข้อมูลล่าสุด), `date_joined` + `created_by` (สร้างบัญชี) — ห้ามแสดงเหตุการณ์ที่ระบบยังไม่เก็บ
- ผู้ใช้ที่ปิดใช้งานแล้วก็เปิดดูได้ / id ที่ไม่มี → `404` (`code: not_found`)

# ฝั่งเขียน

## รูปแบบคำตอบของการเขียนทุกแบบ
สำเร็จตอบ `{ "user": { ...รายละเอียดผู้ใช้เหมือน GET /users/{id}/... } }` และ endpoint ที่อาจส่งอีเมลเพิ่ม **`email_sent`**:
- `true` ส่งอีเมลสำเร็จ / `false` **ส่งไม่สำเร็จ** (การกระทำหลักสำเร็จไปแล้ว หน้าเว็บต้องเตือน Admin ให้กด "ส่งลิงก์อีกครั้ง") / `null` การกระทำนี้ไม่ต้องส่งอีเมล
- ต่างจาก endpoint สาธารณะที่ตอบเหมือนกันทุกกรณี (กันการเดาอีเมล) — ฝั่ง Admin บอกความจริงเสมอ
- ทุกการเปลี่ยนแปลงบันทึก Audit Log ในธุรกรรมเดียวกับการแก้ข้อมูล (ล้มพร้อมกัน) และ **อีเมลส่งหลังธุรกรรมสำเร็จเท่านั้น**

| การกระทำ | สถานะ HTTP สำเร็จ | ฟิลด์เพิ่ม |
|---|---|---|
| สร้างบัญชี | `201` | `email_sent` (`true`/`false`) |
| แก้ข้อมูล | `200` | `email_sent` (`true`/`false`/`null`) |
| ปิด / เปิดใช้งาน | `200` | — |
| ส่งลิงก์ตั้งรหัสผ่านซ้ำ | `200` | `email_sent` (`true`/`false`) |

## `POST /api/admin/users/` — สร้างบัญชี
```json
{ "role": "teacher", "first_name": "วิภา", "last_name": "สุขสวัสดิ์", "email": "wipha.s@example.ac.th",
  "student_or_staff_id": "T0057", "first_name_en": "Wipha", "last_name_en": "" }
```
- **บังคับ:** `role` (`admin`/`teacher`/`student`), `first_name`, `last_name` (ไม่เกิน 150), `email` — **ไม่บังคับ:** `student_or_staff_id` (ไม่เกิน 50, ห้ามมี `@`, ว่าง/`null` = ไม่มีรหัสและเก็บเป็น `NULL`), `first_name_en`, `last_name_en`
- **ฟิลด์อื่นที่ส่งมาถูกทิ้งเงียบ ๆ** (`password`, `is_active`, `is_staff`, `is_superuser`, `is_email_verified`, `created_by`, `id` ฯลฯ) ตั้งสิทธิ์หรือรหัสผ่านทางนี้ไม่ได้
- ชื่อและอีเมลถูกตัดช่องว่างหัวท้าย อีเมลแปลงเป็นตัวพิมพ์เล็ก
- **บัญชีที่สร้าง:** ยังไม่มีรหัสผ่าน (สถานะ `pending_password`), ยืนยันอีเมลแล้วตั้งแต่สร้าง (เจ้าของพิสูจน์อีเมลตอนกดลิงก์ตั้งรหัส), `created_by` = Admin ที่สร้าง, **ไม่ได้สิทธิ์ Django admin** (`is_staff = false` แม้บทบาทเป็น `admin`)
- ส่งอีเมลลิงก์ตั้งรหัสผ่าน (หน้า `/reset-password`) **อายุ 7 วัน ใช้ได้ครั้งเดียว** ไปที่อีเมลนั้น (ตอน dev พิมพ์ลงคอนโซล backend) — เจ้าของกดลิงก์แล้วตั้งรหัสผ่านตามหน้าเดิม (`/api/auth/reset-password/`) ก็เข้าสู่ระบบได้ และสถานะกลายเป็น `active`
- ข้อผิดพลาด `400` `validation_error` **รวมทุกช่องในรอบเดียว** (`error_codes` รายช่อง): `required`, `invalid_choice` (role), `invalid` (อีเมลผิดรูปแบบ), `blank`, `max_length`, `staff_id_contains_at_sign`, **`email_taken`** (อีเมลซ้ำ ไม่สนตัวพิมพ์ รวมอีเมลของบัญชีที่สมัครเองแต่ยังไม่ยืนยัน), **`staff_id_taken`** (รหัสซ้ำ แยกตัวพิมพ์เล็ก/ใหญ่) — ไม่สร้างบัญชี ไม่ส่งอีเมล ไม่เขียน log

## `PATCH /api/admin/users/{id}/` — แก้ข้อมูล
ส่งเฉพาะฟิลด์ที่แก้ (partial) รับ: `role`, `first_name`, `last_name`, `email`, `student_or_staff_id` (ส่ง `""`/`null` เพื่อล้างรหัส), `first_name_en`, `last_name_en` — **รหัสผ่านและสิทธิ์อื่นแก้ผ่านทางนี้ไม่ได้** (ฟิลด์อื่นถูกทิ้ง)
- ไม่มีอะไรเปลี่ยนจริง (รวมกรณีส่งอีเมลเดิมที่ต่างแค่ตัวพิมพ์) → `200` ไม่บันทึก ไม่เขียน log ไม่ส่งอีเมล
- ข้อผิดพลาดเหมือนตอนสร้าง (ไม่นับซ้ำกับตัวเอง) + กฎด้านล่าง
- **บทบาทมีผลทันที** เพราะ backend ตรวจบทบาทจากฐานข้อมูลทุกครั้ง (token เดิมที่มี role เก่ายังใช้ได้ไม่เกิน 15 นาที แต่สิทธิ์จริงเปลี่ยนแล้วทันที — เมนูบนหน้าเว็บอาจเปลี่ยนช้ากว่า)
- **ห้ามเปลี่ยนบทบาทของตัวเอง** → `409` `cannot_demote_self` (ชื่อ/อีเมล/รหัสของตัวเองแก้ได้)
- **ห้ามทำให้ไม่เหลือ Admin ที่ใช้งานอยู่** (ลดบทบาท Admin คนอื่นจนไม่เหลือใคร) → `409` `last_admin`

### เปลี่ยนอีเมล (ได้ทุกบัญชี รวมบัญชีที่ตั้งรหัสแล้ว)
โทเคนในลิงก์ผูกกับ "ผู้ใช้" ไม่ใช่ "อีเมล" ทุกครั้งที่เปลี่ยนอีเมลระบบจึง **ยกเลิกโทเคนที่ยังไม่ใช้ทั้งหมดของบัญชีนั้นก่อน** (ลิงก์ที่เคยส่งไปอีเมลเดิมใช้ไม่ได้อีก) แล้วทำตามสถานะ:

| สถานะ (หลังเปลี่ยน) | สิ่งที่ทำ | `email_sent` |
|---|---|---|
| `pending_password` | ส่งลิงก์ตั้งรหัสผ่าน (7 วัน) ไป**อีเมลใหม่** | `true`/`false` |
| `pending_verification` | ส่งลิงก์ยืนยันอีเมล (24 ชั่วโมง) ไปอีเมลใหม่ ยังไม่ยืนยัน | `true`/`false` |
| `active` | คงสถานะ "ยืนยันอีเมลแล้ว" ไว้ ไม่ส่งอะไร | `null` |
| `disabled` | ไม่ส่งอะไร (ลิงก์ใช้กับบัญชีที่ปิดไม่ได้อยู่แล้ว) | `null` |

- Audit Log บันทึกอีเมลเก่า → ใหม่ (`changes.email = [เก่า, ใหม่]`) **ไม่แจ้งเตือนไปอีเมลเดิม** (ตัดสินใจแล้ว: กรณีหลักคืออีเมลเดิมมีปัญหา) และ **ไม่ตัดเซสชันที่ล็อกอินค้างอยู่** ของบัญชีนั้น
- ถ้าอีเมลใหม่ซ้ำ → `400` `email_taken` และไม่เปลี่ยนอะไรเลย (ลิงก์เดิมยังใช้ได้)

## `POST /api/admin/users/{id}/deactivate/` และ `.../activate/` — ปิด / เปิดใช้งาน
ไม่มี body ทำซ้ำได้ (สถานะเป็นอย่างนั้นอยู่แล้วก็ `200` ไม่เขียน log ซ้ำ)
- **ปิดตัวเองไม่ได้** → `409` `cannot_deactivate_self`; **ปิด Admin คนสุดท้ายไม่ได้** → `409` `last_admin`
- ปิดแล้ว: เข้าสู่ระบบไม่ได้ทันที (ตอบ `invalid_credentials` เหมือนรหัสผิด), access token เดิมใช้ไม่ได้ทันที (`401`), ต่ออายุเซสชันไม่ได้, ลิงก์ตั้งรหัส/ยืนยันที่ค้างอยู่ใช้ไม่ได้ ข้อมูลและประวัติยังอยู่ครบ
- เปิดกลับทันทีไม่ต้องยืนยัน กลับเป็นสถานะตามข้อมูลจริง (เช่นบัญชีที่ยังไม่เคยตั้งรหัสกลับเป็น `pending_password` ไม่ใช่ `active`)

## `POST /api/admin/users/{id}/resend-invite/` — ส่งลิงก์ตั้งรหัสผ่านซ้ำ
ไม่มี body ใช้ได้เฉพาะสถานะ **`pending_password`** เท่านั้น
- ส่งซ้ำได้ **ทุกเมื่อที่พ้น 60 วินาที** จากลิงก์ล่าสุด (ไม่ต้องรอให้ลิงก์หมดอายุ) ลิงก์ฉบับเก่าใช้ไม่ได้ทันที ลิงก์ใหม่อายุ 7 วัน
- `429` `resend_too_soon` เมื่อยังไม่พ้น 60 วินาที พร้อม **`retry_after`** (วินาที) ใน body และ header `Retry-After` — ไม่ส่งอีเมลและลิงก์เดิมยังใช้ได้ (หน้าเว็บแสดง "ส่งอีกครั้งได้ใน N วินาที")
- `409` `invite_not_applicable` เมื่อบัญชีอยู่ในสถานะอื่น (รวมบัญชีที่ปิดใช้งาน)
- กฎรอ 60 วินาทีนับรวมลิงก์ "ลืมรหัสผ่าน" ที่ผู้ใช้ขอเองด้วย (จุดประสงค์เดียวกัน)
- บันทึก Audit Log เป็น `update` ที่ไม่มี `changes` แต่มี `context.event = "resend_invite"`

## รหัสข้อผิดพลาดที่หน้าเว็บต้องแปล (ฝั่งเขียน)
| HTTP | `code` | เมื่อไร |
|---|---|---|
| 400 | `validation_error` (+ `error_codes` รายช่อง) | ข้อมูลไม่ถูกต้อง / อีเมลหรือรหัสซ้ำ |
| 401 / 403 | `not_authenticated` / `permission_denied` | ไม่ล็อกอิน / ไม่ใช่ Admin |
| 404 | `not_found` | ไม่พบผู้ใช้ |
| 409 | `cannot_demote_self`, `cannot_deactivate_self`, `last_admin`, `invite_not_applicable` | ผิดกฎของระบบ |
| 429 | `resend_too_soon` (+ `retry_after`) | ส่งลิงก์ซ้ำเร็วเกินไป |

## ข้อจำกัดที่รู้อยู่
- **ค้นหาแบบเจอบางส่วนของคำทำให้ฐานข้อมูลสแกนทั้งตาราง** เพียงพอสำหรับผู้ใช้หลักพันคน ถ้าเกินหลักหมื่นควรเพิ่มดัชนีแบบ trigram (`pg_trgm`) — บันทึกในเช็กลิสต์ก่อน deploy
- **รายการไม่บอก "ต้องรออีกกี่วินาทีถึงส่งลิงก์ซ้ำได้"** (ต้องคิวรีเพิ่มต่อแถว) หน้าเว็บรู้เวลาจากคำตอบ `429` ของ `resend-invite` หรือนับเองหลังส่งสำเร็จ
- ไม่มี endpoint นับแยก — ตัวเลขบนแท็บมาพร้อมรายการ (`role_counts`) ในคำขอเดียว
- **ตอน dev อีเมลพิมพ์ลงคอนโซล backend** ไม่ได้ส่งจริง (ยังไม่ได้เลือกผู้ให้บริการอีเมล)
- ยังไม่มีจำกัดจำนวนคำขอต่อ IP (ดูเช็กลิสต์ก่อน deploy ข้อ 1) — endpoint ทั้งหมดในหน้านี้ล็อกไว้ให้เฉพาะ Admin
- **การเปลี่ยนอีเมลไม่ตัดเซสชันเดิม:** ถ้าอีเมลเก่าถูกยึด ผู้โจมตีที่ล็อกอินค้างอยู่ใช้ต่อได้จนเซสชันหมดอายุ (สูงสุด 7 วัน) — ทำเพิ่มได้ภายหลังโดยไม่ต้องเปลี่ยนสัญญา API
